# USB 与蓝牙桥接延迟对比

0.1.2 新增主窗口“延迟对比”，覆盖按键、左右摇杆、L2/R2 输入、触碰/滑动/触控板点击、精细震动、R2 阻力开关。0.1.3 改用更小的事件驱动音频缓冲，USB 和桥接对比应使用同一版本；旧版输出标记前排队的音频更长，不能混用版本直接比较绝对间隔。无需进入游戏，不新增驱动或开机项。

## 当前验收边界

模块保存输入报告、绘制回调、输出提交时刻与原始传感器数据，使用同一解析规则、输入阈值和输出信号。物理延迟字段始终留空，须结合真实拍摄材料分析；软件运行成功不等于延迟对比已经完成。

这是独立测试模块在受控条件下的比较，不包含《影之刃：零》自己的输入轮询、帧率、反馈触发和音频缓冲。测得的数值不能直接当作游戏内端到端延迟；它可用于判断连接路径的差异和定位下一步优化。

- 输入视频测的是**可见动作到屏幕响应**，包含机械行程/触发阈值、控制器、传输、软件、屏幕的时间。它不是单独的蓝牙传输延迟。
- 输出视频测的是**屏幕提交标记与可见振动/扳机位移的相对时间**。屏幕标记自身也会延迟，可能晚于反馈出现；同条件 A/B 有参考价值，不能直接称为命令到马达/力的绝对延迟。
- 建立阻力的时刻未必伴随可见位移。视频只能在稳定轻预压下比较释放阻力后的下沉；准确测量力建立需要外部力传感器。不要把没有可见位移解释为没有阻力。
- 报告间隔、Read 到 Paint 回调耗时、音频缓冲和写入耗时只作诊断，不替代上述测量。手柄内部时间戳未与 PC 同步；原始加速度即使能看到振动，也含输入返回路径，不能单独据此得出输出物理延迟。

## 保持条件相同

游戏保持退出；两轮 Steam 状态相同，避免其他映射/测试软件抢占手柄。Bose 可以继续以同样方式播放。测试音频只选择目标手柄的四声道音频端点，不向默认耳机端点发送测试音。

固定显示器刷新率、窗口位置/大小、相机位置/帧率、拍摄照明与手柄摆放；USB 线留松弛量，不牵扯手柄。手机优先用 240fps，120fps 也可。必须保留相机原始慢动作文件；导出文件的 30/60fps 播放帧率不能直接当拍摄帧率。尽可能把手部动作和屏幕响应区放在同一画面、接近相同水平线，减少滚动快门与屏幕扫描的相对影响。

## 第一轮：USB 原生

1. 主窗口先停止桥接并完成恢复。插入 USB 数据线，打开“延迟对比”，点“刷新目标”。选择“物理 USB 原生 · 普通 DualSense”。
2. 手机开始慢动作录制，选择实际拍摄 fps 与测试项，再点“开始本项（3 秒准备）”。倒计时中松开按键、摇杆回中、扳机松开。
3. 按下表操作。输入每次采集 30 秒，可重复同一项目分别拍不同部件。每次只做一种动作，避免其他按钮改变白色响应区。
4. 自动结束或点“停止并保存”。记录区显示 JSON 完整路径；给对应视频使用相同主文件名，保留 USB/项目标识。先确认一段 × 键试拍能清楚看到手指与屏幕，再拍其他项目。

| 项目 | 建议操作与判定 |
| --- | --- |
| 按键 | 每秒按下/松开一次 × 键，至少 20 次。视频分别标可见下压起点、屏幕变白；松开可另列。可见下压不等于电气触点闭合。 |
| 左/右摇杆 | 每次先回中，再向同一方向轻推。左右各至少 10 次，分别统计；保持推法相似。死区 8、累计变化阈值 4，两种连接完全相同。 |
| L2/R2 输入 | 此项不施加阻力。分别轻扣、松开，每侧至少 10 次；死区 2、累计变化阈值 4。可见行程与电气阈值分开理解。 |
| 触控区 | 触碰/离开、滑动、机械按下分开拍，各至少 10 次。接触观察白色响应区；滑动观察坐标点首次移动；点击观察“机械点击”文字。滑动阈值 4。 |
| 精细震动 | 约 19 秒、12 次双侧 150ms 脉冲。稳定放置手柄，可在外壳贴轻薄纸条帮助看清振动，USB/桥接保持相同布置。若视频看不清起振帧，就记为不可判读，不用主观感觉填毫秒。 |
| R2 阻力 | 8 次开启/关闭，约 16 秒；稳定轻预压，避免硬掰。拍清标记和扳机。优先比较关闭阻力后的下沉，不能据此直接测力建立。 |

## 第二轮：蓝牙桥接

1. 等本项完成，关闭对比面板。拔 USB、按 PS 键通过普通蓝牙连接；主窗口启用蓝牙桥接，等连接稳定。
2. 再打开“延迟对比”，确认目标为“虚拟 USB（USB/IP） · 普通 DualSense”。使用相同 fps、项目顺序、操作和相机/手柄布置重拍。
3. 记录结束后关闭面板；主窗口停止桥接并完成恢复，再检查普通蓝牙输入和 Bose 播放。不要在采集进行时插拔 USB。桥接启停会等待本窗口取消和释放测试输出。
4. 若差异很小或两轮操作明显不一致，再补一轮 USB（或 USB→桥接→桥接→USB），不要用单次极值判断。

## 结果计算

每次有效试验保留：模式、项目/左右侧、视频文件、实际拍摄 fps、动作/标记帧、响应帧、是否模糊、对应 JSON。时间差 = 帧差 × 1000 / 拍摄 fps。输出相对间隔允许为负，不应截成 0。

240fps 每帧约 4.17ms，120fps 约 8.33ms；每个边界的判帧不确定性需单独注明。保守按两端各 1 帧处理时，单次区间约 ±2 帧，另有滚动快门、屏幕扫描和动作定义误差。比较中位数、P95、有效样本数与误差，不把低于分辨率的差异判成确定优势。模糊/遮挡/无法看到起点的样本排除并记录原因。

建议输出表分成“输入动作到画面”“输出相对视频间隔”“软件诊断”三部分。准确的电气输入到 PC、命令到振动/力的绝对延迟，需要有共同时间基准的开关/传感器采集。现有手机方案无法替代这类仪器。

## 数据和异常处理

记录位于工具目录 `.local/latency-tests/`，包含采集模式和实际状态。`completed` 仅表示取得有效报告并完成测试流程；`cancelled`、`failed`、`cleanup-failed` 都保留记录。读不到有效 64 字节报告时拒绝开始输出；输入停止 2.5 秒即中断。异常退出或中止会尝试释放阻力/震动。

反馈测试与延迟测试共享进程内及跨进程互斥，防止同一桌面会话中的另一测试进程同时输出。不会自动修改蓝牙、耳机、Steam 设置或启动游戏。
