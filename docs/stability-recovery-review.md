# 0.1.5-dev.3：稳定性、兼容性与退出恢复检查

日期：2026-11-02。基于未发布的 [0.1.5-dev.2](audio-safety-candidate.md) 候选版继续检查。保留 `v0.1.4`、界面候选版与 dev.2 的原程序，本轮单独输出 dev.3，尚未发布或替换日常版本。

本轮使用源码审查、模拟进程、模拟设备配置及本机临时 TCP 端口检查。没有连接或操作真实手柄／蓝牙耳机，没有启用实际桥接、读写真实 HidHide 配置、改驱动或修改系统蓝牙／音频设置。实机兼容性与物理反馈仍需后续验收。

## 已完成的优化

| 方面 | 确定的问题 | 本轮处理 |
| --- | --- | --- |
| 稳定性 | 外部命令退出后，后代进程仍可能持有输出管道；旧超时不覆盖读到 EOF 的等待 | 同一个预算覆盖退出和标准输出／错误读取，回收本次 Job 的进程，限制每条输出流至 1 Mi 字符，区分取消、超时和命令失败 |
| 性能与一致性 | 每轮 HidHide 检查启动四次 CLI，分别读取同一配置 | 单进程完整快照，前后状态标记校验，结束附带 `--cancel`；不降低检查频率，每轮进程启动数从 4 降至 1 |
| 退出响应 | 停止请求没有传入外部命令、HidHide 重试和部分 IPC 等待 | 将取消传入这些等待；恢复操作另用不被用户停止令牌取消的实例，保证停止后仍尝试撤销配置 |
| 原生后端 | 监听线程可能在其使用的同步成员构造完成前启动 | 推迟到构造函数体内启动；不修改正式 USB 会话收发 |
| 原生后端退出 | 本机连接只发半个导入请求时，可让监听线程一直等待 | 仅给导入前的头部／busid 接收增加共用 10 秒绝对期限及停止检查；不会用每次收到字节来延长期限 |
| 时钟兼容 | 连接稳定等待和断连期限依赖 UTC 系统时间 | 用单调计时；保留 25 秒启动、3 秒稳定、1.5 秒音频稳定和 5 秒失联宽限参数 |
| 长时运行 | 退出时整份后端日志读入内存；重复音频纠正说明会持续扩张 | 日志只读首尾各最多 64 KiB，缺少证明时保持未确认；恢复记录中的同类说明去重 |
| 状态写入 | Windows 上原有共享读取与覆盖移动可能阻止原子替换，界面轮询与恢复状态写入存在竞争 | `FileShare.Delete` 配合 `File.Replace` 更新已有文件，正在读取者保留旧快照；首次创建仍用移动，磁盘刷新与写前日志保留 |

减少的是**管理流程中的进程启动与不必要的等待／分配**。没有据此声称 CPU 降低 75%，也没有声称降低物理输入或触觉延迟。

HidHide 的批量命令与 `--cancel` 已核对到项目使用的 [v1.5.230.0 CommandInterpreter](https://github.com/nefarius/HidHide/blob/v1.5.230.0/HidHideCLI/src/CommandInterpreter.cpp) 和 [Commands.cpp](https://github.com/nefarius/HidHide/blob/v1.5.230.0/HidHideCLI/src/Commands.cpp)，而非只依赖新版文档。`--cancel` 跳过命令结束时的配置提交；CLI 自身的初始化／自登记行为仍属于上游实现，不宣称更改了它。批量读取的解析保留对未知输出的拒绝，不把缺失字段猜成“关闭”或“空列表”。

状态文件检查在本机 Windows 文件系统上实测：仅增加共享删除仍不足以让原有覆盖移动成功，必须配合已有文件的替换操作。接口语义参考 [ReplaceFileW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-replacefilew)；不通过先删目标再写入来制造缺失窗口。网络共享、可移动介质及特殊文件系统未进行实机验收。

## 退出桥接与直接退出工具

正常停止和窗口关闭仍走同一个会话停止流程。本轮明确了先后顺序：

1. 先发停止事件；后端执行已有的震动归零、扳机释放、麦克风关闭及虚拟连接退出。
2. 等待并核对本次后端退出；不通过进程名称全局结束其他程序。
3. 按原有写前日志撤销本次手柄隐藏和应用登记，保留其他设备及软件的配置。必要操作失败要留下待恢复状态。
4. 检查默认音频与虚拟端口残留。默认音频保护仍只纠正已确认属于虚拟 DualSense 的新增端点，不强制重连耳机。
5. **上述必要操作执行后**才进行日志证据检查及约 5 秒的设备观察。观察使用独立只读音频进程，不能把音频纠正进程一起变成不可用状态。
6. 保存配置清理结果与设备健康观察结果。二者分开呈现：配置已撤销不等于耳机实际有声，也不等于游戏已重新识别原生蓝牙手柄。

dev.2 的短观察预算可能先结束后续还要执行音频纠正的同一个进程；本版消除了该依赖。诊断不再先于核心配置撤销，`BeforeStop` 保留为空，记录新增 `ExpectedAudio` 来说明最后待保留的音频选择。

### 异常退出与重试

- 用户从输出 A 换到 B 后，最近观察到的 B 写入恢复日志，而非只保存在管理器内存。异常结束后手动恢复可继续使用 B，启动时端点集合仍保留用于原有归属边界。
- 旧的 schema 1 日志仍可读；没有新字段时回退到原先启动快照。不搬移、删除旧程序目录中的恢复记录。
- 针对解除隐藏、撤销应用登记、读取状态、恢复全局开关的操作前／操作后失败，验证再次恢复可以继续完成。日志落盘失败也不会跳过已授权的设备配置撤销。
- 管理进程意外退出而状态文件停在“连接中”或“已连接”时，主窗口改为“恢复待检查”。不会仅凭过时文本宣称仍在桥接或已恢复原生。
- 停止等待期间不提前释放其 `Process` 对象，避免界面轮询与等待退出相互竞争。手动恢复在结束旧后端前再次校验启动时间和程序路径。

**不能保证任意故障都自动还原。** 断电、驱动故障、存储不可写、归属不明的虚拟端口或其他软件同步改配置，仍可能要求人工复核。没有用全局重启蓝牙／音频服务、清空 HidHide 列表、批量拔除 USB/IP 端口来掩盖这些情况；发现真实残留时不能显示“完全恢复”。

## 验证证据

- **233 项 C# 检查通过**：包括既有输入／触觉信号／恢复保护检查，完整配置快照解析，时钟边界，10 个恢复故障注入点的报告及重试，旧日志兼容和陈旧 UI 状态处理；另在 Windows 复现旧共享方式阻止原子替换，并验证新旧快照可并存读取。
- 外部进程故障复现：模拟父命令退出、子进程继续持有管道；原流程设 1 秒预算仍等待约 **4.15 秒**，新流程约 **1.02 秒**结束并回收子进程。另覆盖双流大输出、过量输出、命令失败、参数转义、取消与 HidHide 忙重试。此为合成故障时长，不是日常停止总时长。
- C++ 原有音频、HID 排队、归零、CRC、诊断并发检查通过。新增真实 TCP 环回测试覆盖碎片化合法握手、无数据、慢速逐字节、对端关闭和停止中断；端口由系统临时分配，不使用桥接端口或系统驱动。
- 音频子进程故障检查覆盖查询卡住、父进程退出及只读拒绝写入；新增观察超时不影响另一个纠正进程的检查。
- 核对原有可用程序与 dev.2 文件哈希，核对 USB 描述符及已导入会话的数据处理、蓝牙写出、触觉缓冲和反馈信号范围。以本轮本地 `validation.json` 和构建日志为软件回执。

## 尚未改动的兼容性与性能边界

普通 DualSense 型号限制、USB 身份／描述符、输入解析、扳机输出、蓝牙 HID 写出、精细触觉队列及 3 块／35 ms／12 块／100 ms 参数保持原样。没有关闭虚拟四声道音频端点，也没有缩小缓冲、超频轮询或改系统电源策略。

仍需实际设备完成：

- 原生 USB 与本候选版的全部输入、精细触觉、自适应扳机及静音对照。
- 点击停止与直接关闭窗口两条路径，持续播放 Bose 并用音量键验证实际响度。
- 正常停止后再检查 90 秒，核对虚拟端口消失、原生输入、默认端点和后台进程；再插 USB 验证原生使用。
- 自然待机／重连、运行中更换外部输出、已有其他手柄／HidHide 使用者的共存。手动关机测试不能替代自然待机。

“虚拟端点从首次枚举开始绝不成为默认设备”的驱动策略仍未启用，Bose 无声或音量故障也未宣布彻底修复，详见 [音频隔离研究](audio-isolation-static-review.md)。

当前包内 .NET 为 9.0.22；[Microsoft 支持策略](https://dotnet.microsoft.com/en-us/platform/support/policy/dotnet-core) 显示 .NET 9 支持于 **2026-11-10** 结束。应把 **.NET 10 LTS 迁移**作为正式发布前的独立兼容性工作，验证 WinForms、高 DPI、COM／WASAPI、子进程和恢复流程后再更换随包运行时。本轮保留现有运行时与系统安装状态。

候选目录：`dist/DualSenseBridge-stability-candidate`。本轮不 commit、push、创建 Release 或更新系统依赖。
