# 震动延迟专项优化（0.1.3）

用户在 2026-10-30 手工对比后报告：按键、摇杆、扳机输入、触控和扳机阻力没有明显体感差异，桥接震动仍明显迟于 USB。未拍摄视频，因此“数百毫秒”记录为主观体感，不作为已测得的物理延迟。

## 已定位的问题

1. 0.1.2 独立测试器主动申请 100ms 共享音频缓冲。USB 的一轮完整测试中，脉冲提交时前面已有约 90ms 的样本。这个因素影响测试器，也影响蓝牙桥接测试，但不是桥接独有因素；不能据此推断游戏也用了相同缓冲。
2. 旧桥接测试的 19 个按秒统计样本中，音频队列等待中位数 64.840ms、最大采样值 97.843ms；全流最大等待计数约 99.862ms。USB 音频到达最大间隔计数约 60.234ms。蓝牙写入队列在这些统计点均为 0，不能把持续排队归因于该队列，也不能由此推断无线发送/手柄内部没有缓冲。
3. 原 USB/IP 接收线程同时处理音频 OUT 和 HID IN。没有新输入时，HID IN 会同步等待最多 50ms，挡住后续音频。此处已改成异步待处理请求，输入到达时再生成回复，音频接收继续进行。
4. 原本地 TCP 连接未设置 TCP_NODELAY，部分完整回复分成头部、载荷两次写入。候选修复仅对本服务接受的连接启用 TCP_NODELAY，并将同一回复字节合并发送。第一轮实测说明仅此变更不足：队列采样中位数仍约 64.540ms，因此没有把它宣称为已证实的主因。

统计脚本为 `scripts/analyze-haptics-timing.py`。队列中位数只来自按秒日志采样，不是每个音频包的完整分布；最大计数可能包含采集窗口之前的活动。所有物理延迟字段仍为空。

## 修复与保护

- 独立测试器改为事件驱动、请求至少 20ms 或两个默认音频周期的共享缓冲。当前 USB 实机分配 1056 帧/48kHz，约 22ms；12 次脉冲前排队样本均约 20.021ms，采集完成、输出正常复位。这只描述软件音频缓冲。
- 异步 HID 保留有界输入报告与请求队列，校验重复请求；UNLINK 正确使用已转换为主机字节序的目标序号，成功取消后不会再发送该待处理回复。
- HID 和 ISO 待发送回复携带会话代次；停止时先禁止输入回复入队，再在发送锁内使代次失效。即使 Windows 重用 socket 数值，旧会话已出队的回复也会被拒绝。
- 不修改蓝牙适配器配置、耳机音频参数、全局网络设置或手柄固件；不新增驱动、服务和开机项。
